# 第五章 传输层

🚩重点：

UDP，TCP，TCP 的可靠传输、流量控制、拥塞控制

# 1\. 传输层协议概述

两台主机之间的通信实际上是这两台主机中的应用进程互相通信，通信的真正端点是主机中的应用进程。一台主机中，经常有多个应用进程同时分别和多台其他主机中的应用进程通信。因此，分组到达主机后需要知道自身应该发向哪个应用进程。传输层通过“分用”“复用”来实现。

![h1szytcI\.png](h1szytcI.png)

- 分用：接收方能够把报文正确交到对应的应用进程中。

- 复用：发送给不同应用进程的报文使用同一个传输层协议。

互联网为上层协议提供了两种不同的传输层协议：UDP、TCP。

![TvoZBWyE\.png](TvoZBWyE.png)

---

利用软件端口号 Port 来实现分用和复用。port 使用 16 位二进制充当应用进程的唯一标识符。主机在通信时不仅仅要知道对方的 IP 地址，还要知道对方的端口号。运输层的报文首部中要包含源端口号和目的端口号。

主机某一应用进程的端口号不是唯一不变的，可以修改，但不能和本机上其他应用进程的端口号一致。端口号的作用范围只在本地主机，和其他主机的端口号无关。

运输层的端口号分为 3 类：

- 熟知端口号：其数值为0～1023。这一类端口号由 IANA 组织负责分配给一些常用的应用层程序固定使用，因而所有用户进程都知道。此类端口号需要申请。

- 登记端口号，其数值为1024～49151。属于先到先得，要注册登记避免重复使用。

- 动态端口号，其数值为49152～65535。这类端口号留给客户进程选作临时端口号。

# 2\. 用户数据报协议 UDP

UDP 只在 IP 数据报服务基础上增加了有限的功能\-\-\-端口功能、差错检测。

特点：

- 无连接，减少了开销和时延

- 尽最大努力交付，不保证可靠交付。“只管发，不管能否收到”。实现简单，首部开销小

- 没有拥塞控制

- 面向报文。“上边发什么你转发什么”，不对报文进行拆分或合并。

- 支持一对一，一对多，多对一，多对多。

# 3\. 传输控制协议 TCP

TCP 特点：

- 面向连接

- 每条 TCP 连接只能上点对点连接，即一条 TCP 连接有两个套接字标识

- 提供可靠交付服务。即数据无差错、不丢失、不重复、按序到达。

- 全双工通信。连接两端设有发送缓存和接收缓存。

- 面向字节流。虽然应用程序和 TCP 交互是一次一个数据块，但 TCP 会将数据块看成一连串无结构的字节流。TCP 不保证发送方发出的数据块大小和接收方接收时一样。

![2dRLs8ET\.png](2dRLs8ET.png)

## 3\.1\. TCP 首部格式

![wZphKXEB\.png](wZphKXEB.png)

- 序号：在一条 TCP 连接中传送的数据流中的每一个字节都按顺序编号。序号字段的值是报文第一个字节的序号。

- 确认号：是期待收到的下一个报文的序号。表示确认号之前的数据已经接收。

- 数据偏移：指报文段的数据部分的起始 到 报文段的起始 的距离。实际指的是首部的长度

- URG：=1 时，紧急指针字段有效，表明报文段中包含紧急内容，应尽快交付给应用进程

- ACK：=1 时，确认号字段有效

- PSH：TCP 会将数据缓存等待适合时间发送。PSH=1 时会立即发送。

- RST：=1 时，表明 TCP 连接出现问题，需要重启 TCP 连接

- SYN：=1 时，表明请求建立 TCP 连接

- FIN：=1 时，表明发送方请求断开连接

- 窗口：发送窗口的大小。

- 紧急指针：从报文段数据部分初始到紧急指针所指向的位置为紧急数据内容，要尽快发送

## 3\.2\. TCP 的可靠传输

传输层的 TCP 是提供可靠服务的，即传送的数据不能出现差错、丢失、乱序或重复。TCP 通过滑动窗口协议进行字节流的发送与确认，利用序号和确认号保证数据的完整性和顺序性，并使用超时重传计时器对未收到确认的报文段进行重发。这三者共同组成了 TCP 内部的连续 ARQ 协议实现机制。它结合 GBN 和 SR 协议。

![lU5lnLom\.png](lU5lnLom.png)

![yYiTQ3Us\.png](yYiTQ3Us.png)

![fAWALxrr\.png](fAWALxrr.png)

基本要点：

- 采用滑动窗口协议，窗口大小以字节为单位。TCP 把发送的数据看成一个个字节组成的数据流，**每个字节对应一个序号**。在建立连接时，双方要各自确定**初始序号**。

- 采用的是**累计确认**，确认是对所有按序接收到的数据的确认。**确认号**表示接收方期待下一次收到的数据中第一个字节的序号。

- TCP 连接是**全双工通信**，端点既是发送方又是接收方，可以将确认信息和数据一起发送。接收方在准备回复确认时，可能需要等待此次传输数据的准备时间，这样会有**延迟确认**，若这段时间再有需要回复确认的，则使用**累计确认**方式。

- 收到差错报文要丢弃。收到重复要丢弃并且回复确认报文。

- 若收到**未按序到达**的报文，接收方要**立即对已经接收到的数据回复确认**。并将未按序的报文缓存到接收缓存中，等待缺失序号收齐后一起交给应用层。

- 现实中为了减少计时器的开销，**每个 TCP 连接仅使用一个计时器**。超时计时器仅对最早未被确认的报文段起作用。

---

TCP 的缓存

TCP 两端分别设有发送缓存和接收缓存。应用进程想要发送数据要将数据放到发送缓存中等待发送。应用进程接收数据也是从接收缓存中读取。

发送缓存用来暂时存放：  

发送方应用程序传送给发送方 TCP 准备发送的数据；  

TCP 已发送出去但尚未收到确认信息的数据。  

接收缓存用来暂时存放：

按序到达的，但尚未被接收方应用程序读取的数据  

未按序到达的，还不能被接收方应用程序读取的数据  

---

超时重传时间选择：

互联网环境是动态的，在选择超时重传时间的问题上也是动态的，TCP 采用了一种自适应算法来计算超时重传时间。

- 记录一个报文段发出的时间以及收到相应确认的时间。作差得到往返时间 RTT。

- 采用指数加权移动平均算法计算出平均往返时间 RTTs：

    - 新的 RTTs = （1\-α）\* 旧的 RTTs \+ α \* RTT

- 在使用相同的方法计算 RTT 与 RTTs 之间的差 RTT\(D\)：

    - 新的 RTT\(D\) = （1\-β）\* 旧的 RTT\(D\) \+ β \* \| RTTs  \- RTT \|

- 再根据 RTTs 与 RTTD 计算 RTO：

    - RTO = RTTs \+ 4\*RTT\(D\)

- 由于无法准确测量报文段的 RTT 时，直接将 RTO 增大一倍。

---

快速重传机制：

规定一旦收到 3 个重复的确认报文，则立即重传缺失报文。

![dWdws5Pj\.png](dWdws5Pj.png)

---

选择确认机制：

TCP 的确认方式使用累积确认。它只通告最后一个按序到达的字节。有些报文提前到达，存到缓存中，不会回复确认报文。这些没有别确认的可能会产生超时重传。为了避免无意义的重传，提供了可选的选择确认功能 SACK。TCP 在首部中增加可选字段 SACK，接收方可以将所有的接收到的失序字节序号通知发送方，进行选择确认。

## 3\.3\. TCP 的流量控制

流量控制是为了解决发送方发送速率大于接收方接收速率导致的缓存溢出问题。基本思想是接收方根据自身接收能力控制发送方的发送速率。即接收方控制发送发的发送窗口的大小

- TCP 接收方维持一个接收窗口变量，根据可用缓存大小调整接收窗口的大小。

- 接收方在发送确认报文时，将自己的接收窗口大小通知对方。

- 发送方根据收到的确认号和窗口字段内容调整自己的发送窗口。

---

例：假设接收窗口大小为400 字节， 报文段所携带的数据都是100字节长  

![TRt2T94Z\.png](TRt2T94Z.png)

如果窗口大小从 0 变有时的确认报文丢失怎么办？

为防止接收方发送给发送方的窗口大小更新报文段丢失而导致死锁状态，实际上，当窗口大小变为 0 时，发送方如果有数据要发送，则会周期性地发送只包含1字节数据的窗口探测报文段，以强制接收方发回确认信息并通告接收窗口大小。

## 3\.4\. TCP 的连接管理

建立连接：

TCP 连接建立采用客户/服务器方式。主动建立连接的叫客户，被动等待连接的叫服务器。建立的过程称之为“三次握手”。

![GgePnueo\.png](GgePnueo.png)

连接释放：

通信双方都能提出连接释放的请求，这个过程称为“四次挥手”。最后等待 2MSL 最大报文寿命时间。避免最后一个 ACK 丢失。MSL 是设定好的经验值，RFC 标准规定 120s，实际上 Linux 系统规定 30s。

## 3\.5\. TCP 的拥塞控制

当网络中出现太多分组时，网络性能开始下降，这种情况称为网络拥塞。拥塞控制就是防止过多数据注入到网络中，导致链路过载。

![Hj6WgwRA\.png](Hj6WgwRA.png)

---

为了实现拥塞控制， TCP 连接维护了一个拥塞窗口状态变量 cwnd，网络良好增大 cwnd，网络拥塞减小 cwnd。与流量控制的接收窗口 rwnd 效果类似，通过窗口值来控制发送报文的量。那么 TCP 需要同时考虑流量控制和拥塞控制，则发送窗口大小的上限：

= Min（rwnd，cwnd）

TCP 认为分组丢失的主要原因是网络拥塞，因此，出现分组丢失则认为网络出现了拥塞，并调整 cwnd 大小。通过 3 种算法来进行控制：

慢启动：

建立连接后，先将 cwnd 设置为一个 MSS 数值（经验值，10 左右），每收到一个对新报文段的确认，cwnd 就最多增加一个 MSS 数值，直到出现超时重传，就将 cwnd 设置为 1。

![7RYMpDYm\.png](7RYMpDYm.png)

拥塞避免：

慢启动成指数式增长，为避免后期增长过快，TCP 定义了一个状态变量慢启动门限 ssthresh。cwnd \< ssthresh 时执行慢启动，cwnd \> ssthresh 时将 cwnd 值设为ssthresh，并且每次传输 cwnd 值\+1MSS，将指数增长改成线性增加（加性增）。当超时重传时，将ssthresh 的值设置为当前 cwnd 的一半。

![WRKuJ18e\.png](WRKuJ18e.png)

快速回复:

实际上分组丢失存在两种情况：超时重传、连续收到三个重复 ACK。第二种是某一分组丢失，但后序分组到达的情况。说明网络拥塞程度不高，还有传输数据的能力。为此要做出区分，连续收到 3 个重复 ACK 后， ssthresh 值设置为当前 cwnd 的一半（乘性减）。执行拥塞避免算法
